KNAPP KiSoft SRC System Overview

This page provides comprehensive technical documentation for the KNAPP KiSoft SRC (Shuttle Rack Controller) system. SRC is a software subsystem that manages and controls automated warehouses, typically OSR (Order Storage & Retrieval) systems. The documentation covers the core components of the system, from the physical warehouse design to the software processes that control material flow, communication with external systems, and system configuration in a Linux environment.

Each section below corresponds to a core component or process of the SRC system. Use the navigation menu to jump directly to the section of interest.

OSR Warehouse Model: A Comprehensive Guide

The warehouse model is a critical Python configuration file (wh_model_cfg.py) that describes the complete physical and logical structure of an OSR (Order Storage & Retrieval) system. It serves as the primary architectural document, and its correct configuration is essential for system installation and operation.

Executing the configuration script generates a wh_model.xml file, which has two main purposes:

  • Database Initialization: It provides the data needed by the osr_create_instance script to populate the database with all locations, transporters, and other structural elements.
  • Runtime Process Configuration: Several key processes (like spider, grid, and shuttle) read the XML file directly at runtime to get information about the physical layout of the warehouse.

Core Concepts

Cardinal System Orientation

The OSR model uses a fixed cardinal system for orientation to ensure consistency across projects. This system is based on a single, fundamental rule:

  • The area containing the container lifts is always defined as being in the South.
  • Based on this, all other directions are determined: North is the rear of the OSR, East is to the right, and West is to the left when facing the aisles from the lift area.
  • Storage locations are always numbered from South to North.

Hierarchical Structure

The warehouse is defined using a bottom-up hierarchy, which allows for complex layouts to be built from simple, reusable components. The order is from the smallest unit to the largest:

  1. Location: The smallest unit. It is a single, addressable position in a rack where one or more containers can be stored (in multi-deep systems). A multi-deep position is still only a single location entry in the database; the depth is stored in the loc_max_pos column.
  2. Module: A physical segment of a rack, typically enclosed by vertical posts, which contains a defined set of locations.
  3. Sector: A collection of modules that form a continuous rack line. In a 1D system, a sector is one full side of an aisle.
  4. Aisle: The space between two rack lines (sectors) where a shuttle operates.

Configuration Parameters

General Settings

osr_id
A crucial string that identifies the OSR instance (e.g., "osr1"). All database entries and directory structures are tied to this ID.

osr_id = "osr2"

Aisle & Level Structure

aisles, aisle_east, aisles_increasing
These three parameters define the aisle numbering scheme.
  • aisles: The total number of aisles.
  • aisle_east: The number of the rightmost (easternmost) aisle.
  • aisles_increasing: A boolean. False means numbers increase from West to East (left-to-right). True means numbers increase from East to West (right-to-left).

# OSR with 8 aisles, numbered 8-7-6-5-4-3-2-1 from West to East.
aisles = 8
aisle_east = 1
aisles_increasing = True
level_struct
A dictionary defining the vertical structure for aisles, including the total number of levels, the position of service levels, and level heights. If heights are different, a list of cumulative heights from the ground up must be provided.

level_struct = {
    # Rule for Aisles 1 & 2: 10 levels, service levels at 1 and 6, uniform height.
    (None, [1, 2]): (10, [1, 6], 425),
    # Rule for Aisle 3: 12 levels, service levels at 1 and 7, and a list of cumulative heights.
    (None, 3): (
        12,
        [1, 7],
        [450, 900, 1350, 1800, 2250, 2700, 3125, 3550, 3975, 4400, 4825, 5250]
    )
}

Container Types

container_types
A list defining all possible container types used for storage, including their physical dimensions. An entry for "UNKNOWN" with db_id = 0 is mandatory.

container_types = [
    # db_id, handling_type, name, length, width, offset, ...
    (1, 1, "OSR_TRAY",    600, 400, 0, 90, 25, 2, 14, 700, 700, 1, 1),
    # A container with a lid has a different handling_type and an offset.
    (3, 3, "LIDDED_TRAY", 600, 400, 25, 90, 25, 2, 14, 700, 700, 1, 1)
]

Aisle Layout Hierarchy

location_types
A dictionary defining every type of location, including storage racks, buffers, and entrances/exits. For multi-deep storage, the z_positions list contains multiple values, representing the starting position of each container within the single location.

"RACK_3DEEP": (7, "storage_3deep", 0, 0, 0, 2, "all", "rack", [48, 688, 1328], 475, 1978, 'middle', 'check_when_suspicious', False),
module_types_logical
Defines the logical composition of a module, specifying which location types it contains and how many.

# A standard module ("STD") contains 4 double-deep locations.
"STD": ("STD", {None: (["LOC"] * 4, 82)}),
# A custom module ("STD_3LOC") with only 3 triple-deep locations.
"STD_3LOC": ("STD", {None: (["RACK_3DEEP"] * 3, 82)}),
sector_types_logical
Defines the logical composition of a sector (a full rack line), specifying the sequence and number of modules it contains.

# A standard rack: 1 LIFT module followed by 25 storage modules.
"RACK": ["LIFT"] + 25 * ["STD"],
# A custom rack for Aisle 3: 1 LIFT, 5 standard, and 1 custom 3-location module.
"RACK_3DEEP": ["LIFT"] + 5 * ["STD"] + ["STD_3LOC"],
aisle_layout
The final step, this list brings all the components together, assigning sector types to the left and right sides of each aisle on specific levels.

# Apply the new RACK_3DEEP layout to both sides of Aisle 3 for all its levels.
(3, 3, None, [("RACK", "RACK_3DEEP", "RACK_3DEEP")], 1, 1),

Exceptions and Transporters

missing_locations
A list that defines locations that exist in the layout but are physically unusable due to obstructions like building pillars or shuttle lifts.
Important: The module number used in a rule is its absolute index in the sector_types_logical list. If a sector starts with a ["LIFT"] module, the first storage module is index #2, not #1.

missing_locations = [
    # Rule: The last module (module #7) in aisle 1 on the left side is unusable on all levels.
    (1, None, 7, None, 'left'),

    # Rule: The first location in the second storage module (module #3)
    # on the left side of service levels [1, 6] in aisles [1, 2] is unavailable.
    ([1, 2], [1, 6], 3, 1, 'left'),
]
picking_stations
A list defining all picking stations connected to the OSR. When the instance is created with the --force flag, opa processes are automatically created for each entry.

picking_stations = [
    (1, "kp2101", None, "POOL", 1, None, None),
    (2, "kp2102", None, "POOL", 1, None, None),
]

Practical Exercise: OSR1 Location Calculation

Step 1: Calculate Gross Theoretical Locations

This is the total number of storage spots before considering any missing locations.

  • Aisles 1 & 2: 2 aisles × 10 levels/aisle × (6 modules/level × 4 locations/module) = 480 locations.
  • Aisle 3: 12 levels × ((5 modules × 4 locations/module) + (1 module × 3 locations/module)) = 276 locations.
  • Total Theoretical Gross: 480 + 276 = 756 locations.

Step 2: Calculate Total Missing Locations

These are the locations removed by the missing_locations rules.

  • Shuttle Lift Rule (Aisle 1): The last module (#7) is unusable. It's a standard module with 4 locations and affects all 10 levels of Aisle 1.
    • Locations to remove: 10 levels × 4 locations = 40 locations.
  • Service Level Obstruction Rule: One location is missing on each service level of each aisle.
    • Aisles 1 & 2 (service levels 1 & 6): 2 aisles × 2 service levels × 1 location = 4 locations.
    • Aisle 3 (service levels 1 & 7): 1 aisle × 2 service levels × 1 location = 2 locations.
    • Total service level locations to remove: 4 + 2 = 6 locations.
  • Total Missing Locations: 40 (shuttle lift) + 6 (service levels) = 46 locations.

Step 3: Final Net Count

  • Final Expected Count: 756 (Gross) - 46 (Missing) = 710 locations.

SQL Verification

To verify the count in the database, the following SQL query is used. It counts entries in the LOCATIONS table, filtering for the specific OSR instance and the location type corresponding to a storage rack.


SELECT
  COUNT(*)
FROM
  LOCATIONS
WHERE
  LOC_OSR_ID = 'osr1'
  AND LOC_TYPE_ID = 0;

Adapter Processes Configuration Exercise (OSR1)

This guide explains the required modifications to the adapter process configuration files (grid_cfg.py, shuttle_cfg.py, and plc_adapter_cfg.py) to match the updated warehouse model for the OSR1 instance.

PLC Station Numbering Convention

In recent SRC versions, PLC stations are identified using a standardized 5-digit number. This convention is critical for correctly configuring the plc_adapter_cfg.py and steuer_cfg.py files.

The structure is as follows: <Floor><Conveyor-Level><Station-Type><Counter>

  • Digit 1 (Floor/Mezzanine): Denotes the floor of the building where the station is located (e.g., '1' for ground floor).
  • Digit 2 (Conveyor Level): Identifies the conveyor's height level, counted from bottom to top.
  • Digit 3 (Station Type): Describes the function of the station.
  • Digits 4-5 (Counter): A sequential counter for stations of the same type, typically starting at '00'.

Common Station Types (Digit 3)

The third digit defines the station's role. Here are some of the most common types:

  • 4: Helper station in the prezone (e.g., loop switch).
  • 5: Entrance to an OSR aisle.
  • 6: Lift station.
  • 7: Diversion to a picking station.
  • 8: Picking station.
  • 9: Lift entrance reading point.

Therefore, a station number like 11600 would signify: Ground Floor (1), lowest conveyor level (1), a Lift (6), and it is the first one in the sequence (00).

1. grid_cfg.py Modifications

Requirement: Account for all shuttles required for the new 3-aisle OSR structure.
Explanation: The original OSR had 2 aisles with 10 levels each (20 shuttles). The new OSR has two 10-level aisles and one 12-level aisle, for a total of 32 shuttles ((2*10) + (1*12) = 32). The original script calculated the shuttle count dynamically, but this formula is now incorrect because not all aisles have the same number of levels. The most direct solution is to manually calculate the correct total and hard-code it.

Original Code


# The original script calculates the shuttle count dynamically.
# This works only when all aisles have the same number of levels.
aisleCount = 2
levelCount = 10
...
shuttleCount = (aisleCount * levelCount) + spareShuttleCount

Modified Code


# The aisle and level counts are kept for reference, but the final count is hard-coded.
aisleCount = 2
levelCount = 10
...
# shuttleCount = (aisleCount * levelCount) + spareShuttleCount
shuttleCount = 32 # Hard-coded to the correct total of 32 shuttles.
...
# The rest of the script uses this shuttleCount to create the list of transporters.
shuttleRange = range(startShuttleNr, startShuttleNr + shuttleCount)

4. Answering the Questions

Q1: What (system) settings would have to be done for the shuttles outside of the Python configs?

Answer: The most critical system setting that must be configured outside of the Python files is the network configuration on the Linux server.
The shuttle adapter process communicates with each physical shuttle over a TCP/IP network. For this to work, the server must be able to resolve the shuttle hostnames (e.g., shuttle0001, shuttle0002, etc.) to their correct IP addresses.

Example Setting: This is typically done by adding entries to the /etc/hosts file on the server. An entry would look like this:


# This line maps the IP address of a shuttle to its hostname.
192.168.10.21    shuttle0021

Q2: What happens if you try to execute a shuttle Python config from the templates folder?

Answer: If you try to execute a shuttle_cfg.py file directly from the templates folder without modifying it, the script will fail with a syntax error.

Reasoning: This is an intentional safety mechanism. The template files contain special, invalid Python syntax markers like !TODO! placed in front of critical hardware-related parameters (e.g., motor power, timeouts, physical dimensions). Executing the script with incorrect default values for these parameters could cause serious physical damage to the expensive shuttle and rack hardware. Forcing the developer to manually find and remove these !TODO! markers ensures that they have consciously reviewed and correctly set these safety-critical values before the configuration can be loaded.

The 'steuer' Process: A Comprehensive Guide

The steuer process is a central component of the KiSoft SRC (Shuttle Rack Controller) system. It acts as the primary logic and control process for a single OSR instance, managing the entire material flow within the prezone and coordinating tasks between the warehouse and the picking stations. Its main task is to ensure proper routing of source and target containers to their designated destinations.

1. Core Responsibilities & Concepts

The steuer process controls the flow of containers through the conveyor system and is responsible for ensuring containers arrive at the correct stations in a timely manner.

1.1. Key Concepts

  • Prezone: The conveyor system connecting the OSR lifts to the picking stations, which is controlled by the steuer process.
  • Source & Target Containers: Source containers hold items to be picked from the OSR. Target containers are the destination for picked items (e.g., a customer's order).
  • Fetching & Pre-fetching: Fetching is the process of retrieving a source container from the OSR for a current picking order. The number of containers is defined by the fetch parameter. Pre-fetching is a proactive strategy to retrieve containers for upcoming orders in advance, defined by the prefetch parameter. The containers are buffered on the lift exits to minimize wait times.
  • PLC Stations: These are physical points on the conveyor system that the steuer process controls.
    • Loop Switch: A PLC station on the source container loop. They are defined in the loopSwitchSequence.
    • Diverter: A PLC station on the target container line. They are defined in the genericDiverterSequence.
    • Fill Reader: A specific loop switch, usually the last one before the OSR aisles, where the decision is made about which aisle a container will be sent to for storage.

2. Configuration (steuer_cfg.py)

The behavior of the steuer process is defined in the steuer_cfg.py configuration file. This file uses several key Python objects and lists to map the physical layout and logical rules of the prezone.

2.1. Main Configuration Blocks

  • towerMFSequence: Defines the sequence of lifts (towers/aisles) and their associated material flow controllers.
  • pickStationSequence: A list of all picking stations connected to the instance, including their ID, fill reader, and capacity.
  • loopSwitchSequence: Defines the loop switches that control entry into picking station loops or aisles.
  • layout: A dictionary that defines all physical PLC stations in the prezone.
  • loopLayout: A list that holds all the routing information. It explains for each station which destinations can be reached and what direction a container must take. This is the most critical part of the routing logic.

2.2. The loopLayout: The Routing "Road Map"

The loopLayout is a list where each item defines the possible routes from a single, specific PLC station. It acts as a comprehensive "road map" for the entire conveyor system. It uses two main building blocks:

  • OSR.SteuerCfg.Routes(station_id, [route_entries]): This object is the main container. It associates a starting PLC station ID (e.g., 12502) with a list of all possible paths leaving that station.
  • OSR.SteuerCfg.RouteEntry(direction, [targets], preannounce_station): This object defines a single path from the station.
    • direction: The numeric code sent to the PLC to take this path (e.g., -1 to divert, 0 to go straight).
    • [targets]: A list of all final destinations (like aisles or picking stations) that can be reached by taking this path.
    • preannounce_station: The ID of the next PLC station that should be notified in advance that this container is coming. A value of 0 means no pre-announcement is made.
Understanding Routing Shortcuts

To avoid listing every single station ID for common routes, the configuration uses a powerful shortcut notation within the target list in the format "<TARGETS><FLOOR_ID>:<SEGMENT_ID>".

  • The letters represent groups of stations:
    • F: All Fill readers.
    • P: All Picking stations.
    • T: All Towers (aisles).
  • The numbers identify the specific conveyor loop (Floor) and Segment the targets belong to.

For example, "FP0:0" expands to mean "All Fill readers and all Picking stations on Floor 0, Segment 0".

3. Practical Example: OSR1 Modifications

This case study demonstrates how to modify the steuer_cfg.py file to accommodate physical changes in the warehouse for the OSR1 instance.

3.1. Requirement: Add a Third Aisle

The steuer process must be made aware of the new aisle (tower) to interact with it.

Solution

The new aisle is added to the towerMFSequence and referenced in the main layout definition.


# Modified towerMFSequence now includes aisle 3.
towerMFSequence = [
    getTower(1, 99.5),
    getTower(2, 99.5),
    getTower(3, 99.5)
],

# Within the layout definition, the towerRefSequence is updated.
towerRefSequence = [1, 2, 3],

3.2. Requirement: Add a New Picking Station

A new picking station, ps4 (ID 1104), must be added with doubled container capacity.

Solution

A new picking station object is created with doubled capacity values (overload, fetch, prefetch) and added to the main sequence.


# Define the new picking station 'ps4' with doubled capacity values.
ps4 = createDefaultPickStationConfig(1104, 10, 12, 24, 20, 40)

# Add the new station to the sequence. The order reflects the physical layout.
pickStationSequence = [ps3, ps1, ps2, ps4],

3.3. Requirement: Configure Station 1104 as a Weight Error Station

The new picking station (1104) must also serve as a dedicated error station for containers with weight errors only.

Solution

The errorStationSequence in the layout definition is modified. A new, specific rule is added for station 1104 and the WEIGHT_EXCEEDED error type, while the general rule for station 1101 is kept for all other errors.


errorStationSequence = [
    OSR.SteuerCfg.ErrorStationStruct(
        id = 1101,
        errorTrayTargetLocation = "",
        errorTypes = [OSR.SteuerCfg.ALL]
    ),
    OSR.SteuerCfg.ErrorStationStruct(
        id = 1104,
        errorTrayTargetLocation = "",
        errorTypes = [OSR.SteuerCfg.WEIGHT_EXCEEDED]
    )
]

3.4. Requirement: Add New PLC Stations and Routing

The physical PLC stations for the new aisle and picking station must be defined, and the system's routing table (loopLayout) must be updated.

Solution

First, the new PLC stations are defined. Then, the loopLayout is updated to integrate them.


# This example is for the new PLC station 12502, the entrance switch for Aisle 3.
# A container arrives at station 12502.
# If its destination is Aisle 3, steuer sends direction -1 to the PLC to divert.
# If its destination is another Picking station, steuer sends direction 0 to continue straight.
OSR.SteuerCfg.Routes(12502, [
    OSR.SteuerCfg.RouteEntry(  0, ["FP0:0"], 0),
    OSR.SteuerCfg.RouteEntry( -1, ["3"], 0)
]),

# This example is for the new diverter 11703, which controls entry to picking station 1104.
# A container arrives at 11703.
# If its destination is station 1104, steuer sends direction -1 to divert into the station.
# If its destination is the main exit (91), steuer sends direction 0 to go straight.
OSR.SteuerCfg.Routes(11703, [
    OSR.SteuerCfg.RouteEntry(  0, ["91"], 91),
    OSR.SteuerCfg.RouteEntry( -1, ["1104"], 1104)
]),

4. FAQ & Troubleshooting

Q: Where can I find information on available error types for an error station?
A: There are two primary sources:
  1. The IDL File (Definitive Source): The formal definitions are in the Interface Definition Language file, steuer_cfg.idl. It contains an enum ErrorType which lists all possible constants, such as WEIGHT_EXCEEDED, HEIGHT_EXCEEDED, UNKNOWN_TRAY, and ALL.
  2. Existing Code (Practical Source): A common approach is to search for errorStationSequence in the source code of other projects. This provides practical examples of how different error types have been implemented previously.
Q: What steps are required to implement a new, second exit from the system?
A: Adding a new physical exit requires coordinated changes across multiple parts of the system:
  1. Warehouse Model (wh_model_cfg.py): A new conveyor of type="exit" must be defined in the conveyors list.
  2. PLC Adapter Config (plc_adapter_cfg.py): The new PLC station that physically controls the exit diverter must be defined so the system can communicate with it.
  3. Steuer Config (steuer_cfg.py):
    • The new exit's virtual station number (e.g., 92) must be added to the exitStationSequence.
    • The corresponding physical PLC station number must be added to the loopSwitchSequence.
    • The loopLayout must be updated to include a route from a decision point to the new exit 92.
  4. Database Verification: After deployment, you must verify that a new location for the exit was created in the LOCATIONS table and is correctly assigned to the steuer transporter in the TRANSPORTER_LOCATIONS table. This final step is crucial for steuer to recognize the exit as a valid destination.

General Overview

The Host Input/Output (HIO) is the software interface on the KiSoft SRC (Storage & Retrieval Controller) side responsible for communication with the "outside world," typically a warehouse control system (WCS). SRC is usually a subsystem within a larger warehouse, controlling a specific area like an OSR, and thus receives orders from and sends status updates back to the WCS. This communication is handled by two primary processes: hio_cmd for receiving orders and hio_status for sending status updates.

Key Concepts

  • Marshalling / Unmarshalling: The process of converting data into XML format (marshalling) and back (unmarshalling).
  • DTD (Document Type Definition): A file, hio.dtd, that formally describes the structure of the XML messages, including all legal elements and attributes. It is typically located at /kisoft/build/src/java/at/syslog/osr/hio/hio.dtd.
  • Regex (Regular Expression): A sequence of characters that defines a search pattern, used in configuration to describe allowed formats for values.

Architecture

The HIO interface consists of two independent processes, each listening on a dedicated TCP/IP port. This separation creates a command channel for incoming orders and a status channel for outgoing status updates.

  • hio_cmd: The "command channel" process that receives orders and information from the host system. Its default port is 9803.
  • hio_status: The "status channel" process that sends status information about orders back to the host. Its default port is 9804.

These processes interact with the SRC database, which is split into two schemas:

  • osr schema: Stores the main application data.
  • osr_aq schema: A message queue system (Oracle Advanced Queuing) for inter-process notifications.
HIO Communication Channels
Channel Direction Process Default Port
Command Channel HOST → SRC hio_cmd 9803
Status Channel SRC → HOST hio_status 9804

Communication Protocol

Communication between the WCS and SRC is performed by sending plain text XML messages encoded in UTF-8 over a TCP/IP connection. A critical feature of the protocol is that every message must be acknowledged by the recipient. If a connection is lost, any unacknowledged messages are resent upon reconnection to prevent data loss.

All messages are enclosed within specific wrapping tags:

  • <host2osr> ... </host2osr>: A message from the host to SRC, received by hio_cmd.
  • <host2osr_reply> ... </host2osr_reply>: The acknowledgment from hio_cmd back to the host.
  • <osr2host> ... </osr2host>: A message from SRC to the host, sent by hio_status.
  • <osr2host_reply> ... </osr2host_reply>: The acknowledgment from the host back to hio_status.

Message Flow

Host → SRC (hio_cmd)

  1. XML Message Received: The hio_cmd process receives an XML message from the host.
  2. Unmarshalling: The process converts the XML data into internal Java objects.
  3. Data Verification: The data is validated against configured rules, such as regular expressions in the meterList. If the message does not adhere to the structure defined in hio.dtd, it is rejected.
  4. Acknowledge: hio_cmd sends an acknowledgment reply back to the host. This reply will be successful (e.g., <transport_order_ack>) or contain a descriptive error if the message was faulty.
  5. Persist Data: hio_cmd writes the order information into the osr database schema by calling Oracle packages and procedures.
  6. Inform Other Processes: A message is placed on the Oracle Advanced Queue (osr_aq) to notify other SRC processes (like steuer) about the new order.

SRC → Host (hio_status)

  1. Message from AQ: The hio_status process is notified by the Oracle Advanced Queue (AQ) that an event has occurred which needs to be reported to the host (e.g., an order has been completed).
  2. Get Additional Data: hio_status queries the osr schema to gather all necessary details related to the event.
  3. Marshalling: The collected data is "marshalled" or encapsulated into the proper XML format.
  4. XML Message to Host: The XML message is sent to the host via the status channel.
  5. Acknowledge: The host sends back an acknowledgment reply (e.g., <transport_order_finished_ack>).
  6. Message Consumed: Once the host acknowledges the message, hio_status confirms this in the AQ. After all subscribers have consumed the message, it is removed from the queue.

Configuration

The configuration for both HIO processes is managed in a single Python file, typically hio_cfg.py, located in the instance's cfg folder.

Key Configuration Parameters

  • compartmentConversionList / containerTypeConversionList: These lists map human-readable XML names for container compartments (e.g., "full", "half") to the cryptic internal database codes (e.g., "16R", "8R").

# Example for source containers
compartmentConversionList=[
  OSR.HioCfg.CompartmentConversion(xmlName="full", dbName="16R"),
  OSR.HioCfg.CompartmentConversion(xmlName="half", dbName="8R"),
  OSR.HioCfg.CompartmentConversion(xmlName="quarter", dbName="4R"),
]
  • commandListener / statusListener: These sections contain settings for the hio_cmd and hio_status channels. The most commonly modified parameter is the port number, which must be unique if multiple OSR instances are running on the same system.

commandListener=OSR.HioCfg.Listener(
  port=9803,
  # ... other settings
)

statusListener=OSR.HioCfg.Listener(
  port=9804,
  # ... other settings
)
  • orderProcessorList: This list enumerates all order types the interface can understand and maps them to the corresponding Java classes that process them. This list is rarely modified.
  • meterList: This list defines validation rules for attribute values sent via HIO messages. This feature is no longer relevant in recent SRC versions, but may be present in older systems.
  • pictureDownloader: Configures settings for downloading product pictures from a repository (e.g., an FTP server) to be displayed at workstations.

The Spider Process

The spider process is the central software component responsible for managing and controlling the movement of goods within an automated warehouse. It acts as the brain of the warehouse, coordinating the actions of various hardware components to ensure efficient and accurate storage and retrieval of items.

Overview

The spider process is a sophisticated software system that manages the entire lifecycle of transport orders within the warehouse. It receives commands from a higher-level warehouse management system (WMS), translates them into concrete actions for the hardware, and monitors their execution.

Functions and Connections

The primary functions of the spider process include:

  • Order Management: Receiving, queuing, and processing transport orders.
  • Resource Allocation: Assigning tasks to available hardware resources like shuttles and conveyors.
  • Pathfinding: Calculating the optimal routes for transporting goods.
  • Real-time Monitoring: Tracking the location and status of all transport units (TUs).
  • Error Handling: Managing and recovering from unexpected events or hardware failures.

The spider process is connected to several other systems:

  • PLC (Programmable Logic Controller): The spider communicates with the PLC to control the physical hardware.
  • Shuttles: The spider directly controls the movement and actions of the warehouse shuttles.
  • Steuer (Control System): The spider is a sub-component of the larger warehouse control system.

Spider Workflow

The workflow of the spider process can be summarized as follows:

  1. Order Reception: The spider receives a transport order from the WMS.
  2. Event Queuing: The order is placed in an event queue, waiting to be processed.
  3. Scheduler Assignment: A scheduler picks up the order from the queue.
  4. Task Execution: The scheduler breaks down the order into a series of tasks and assigns them to the appropriate hardware resources.
  5. Monitoring and Completion: The spider monitors the execution of the tasks and marks the order as complete once all tasks are finished.

Core Components

  • Database Persistence: The spider process uses a database to store its state, ensuring that it can recover from restarts without losing track of ongoing operations.
  • Transporters: Software objects that represent a physical piece of hardware, such as a shuttle or a conveyor belt.
  • Schedulers: The decision-makers of the spider process.
  • Orphans and UFOs: An orphan is a transport unit (TU) that has been successfully stored but not yet committed to the database. A UFO (Unidentified Flying Object) is a TU that is detected but has no corresponding record in the database.
  • Routes and the Reachability Graph: A route is a sequence of locations. The reachability graph represents all possible paths within the warehouse.
  • Zones: The warehouse is divided into zones (Composite Zones, Storage Zone Tree) to facilitate efficient management.

Configuration

The spider process is configured through a Python file, typically named spider_cfg.py. The structure of this configuration is defined by an IDL file (spider_cfg.idl).

OPA Process and Picking Station Guide

OPA Process: Core Concepts

General Function

  • opa (order picking area) is one of the three main processes of SRC and is responsible for handling the picking stations.
  • There is one opa process for each physical picking station in the system.
  • If pick-to-light hardware is used, there will also be one corresponding p2l process for each station.
  • Despite multiple processes running, there is only one central configuration file for all opa processes (pickstation_cfg.py).

Picking Station Order Types

The opa process handles several types of orders, which are either selected by the operator or generated automatically by the system.

User-Selectable Orders
  • Picking Order: The main task of picking articles from source trays into target containers.
  • Goodsin / Goodsadd: Placing new articles into empty (goodsin) or partially filled (goodsadd) source trays for storage in the OSR.
  • Merge Order: Consolidating stock from multiple source trays into one to create empty trays.
  • Defrag Order: Moving stock from one tray into an empty slot of another multi-compartment tray.
  • Inventory Order: Manually counting stock in a source tray to verify or correct the system's inventory data.
System-Generated Orders
  • Zero Check: A confirmation step to ensure a source tray is empty after the last item has been picked.
  • Reading Error Order: Generated when a tray's barcode cannot be read automatically. The picker is prompted to scan the barcode manually.
  • Height/Weight Error Order: If a tray fails a height or weight check on the conveyor system, it is sent to a designated error station for the picker to correct the issue.

Physical Station Components

  • Hardware Equipment: A thin client computer, touch screen, barcode scanner, printer, scale, and P2L (pick-to-light) buttons.
  • Structural Components: Source Bays for incoming trays and Target Bays for outgoing containers. Optional sorting mechanisms like a mini loop or sequencer bays.

Behavior Customization (Modules & Attributes)

The specific workflow at a picking station can be customized by adding code Modules to the configuration for different order types. The behavior of these modules can be fine-tuned using Attributes.

GUI Configuration (XML)

The Graphical User Interface (GUI) on the picking station's touch screen is not defined in the Python configuration file. Instead, its layout is constructed at runtime from a set of XML files located in the instance's cfg/forms/ directory.

Question 1: What will you have to do (on top of the config file) for an additional picking station?
Answer: Besides updating the configuration files (wh_model_cfg.py, steuer_cfg.py, pickstation_cfg.py, plc_adapter_cfg.py), setting up a new physical picking station requires several system-level steps:

The ktf tool uses less to display logs. These commands help you navigate.

  • q: Quit the viewer.
  • Spacebar or f: Move forward one page.
  • b: Move backward one page.
  • g: Go to the beginning of the file.
  • G: Go to the end of the file.
  • /pattern: Search forward for a pattern.
  • ?pattern: Search backward for a pattern.
  • n / N: Repeat the previous search.
  • Shift + F: Enter "follow" mode. Press Ctrl+C to exit.

12.4. Basic vi Editor Commands

vi has two main modes: Command mode and Insert mode.

Command Mode (Default)
  • i: Enter Insert mode.
  • Esc: Exit Insert mode.
  • dd: Delete the current line.
  • :w: Write (save).
  • :q: Quit.
  • :q!: Quit without saving.

Advanced SQL Queries

-- Find all containers on a specific level (e.g., level 8) of OSR 1.
SELECT
    a.loc_external_code, b.*, c.*
FROM
    locations a
JOIN
    CONTAINER_LOCATIONS b ON b.cl_loc_id = a.loc_id
JOIN
    containers c ON c.cont_id = b.cl_cont_id
WHERE
    a.loc_external_code LIKE '%.008%' AND a.loc_osr_id = '1';

-- Find all empty containers on a specific level using a regular expression.
SELECT cont.CL_CONT_ID
FROM CONTAINER_LOCATIONS cont JOIN LOCATIONS loc
ON cont.CL_LOC_ID=loc.LOC_ID
JOIN CONTAINERS ct on cont.CL_CONT_ID=ct.CONT_ID
WHERE cont.CL_OSR_ID=2 AND REGEXP_LIKE(loc.LOC_EXTERNAL_CODE, 'S01\\.003.?') AND ct.CONT_EMPTY=1;

-- Update a system property directly in the database (e.g., enable a feature).
UPDATE OSR_PROPERTIES

WHERE OPR_OSR_ID=1 AND OPR_PD_ID='9';
COMMIT;
